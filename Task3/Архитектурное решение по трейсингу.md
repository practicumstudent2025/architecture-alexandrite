# Архитектурное решение по трейсингу

## Анализ системы для трейсинга

### **Критичные системы**:
- **Shop API, CRM API, MES API** - основные бизнес-процессы
- **RabbitMQ** - передача сообщений между системами
- **Databases** - хранение данных заказов и расчетов
- **S3 Storage** - хранение 3D-моделей

### **Ключевые точки сбоев**:
1. **Создание заказа** (Shop → CRM) - потеря сообщений в RabbitMQ
2. **Расчет стоимости** (CRM → MES) - перегрузка MES, медленная обработка
3. **Обновление статуса** (MES → CRM) - потеря сообщений, каскадные сбои
4. **Загрузка файлов** (Shop → S3) - проблемы с сетью, сбои S3
5. **Аутентификация** - истекшие токены, сбои авторизации

## Данные для трейсинга

- **Order ID, Trace ID, Span ID** - идентификаторы для связывания операций
- **Timestamp, Duration, Status** - время и результат выполнения
- **Service Name, Operation Name** - сервис и операция
- **User ID, Order Status** - бизнес-контекст
- **HTTP Status, Error Message** - технические детали
- **Request ID, Session ID** - связывание запросов

## Мотивация

### **Проблемы**: Отсутствие видимости, долгая диагностика, потеря заказов, недовольство клиентов
### **Решение**: Полная видимость пути заказа, быстрая диагностика, предотвращение потерь
### **Результат**: Сокращение MTTD/MTTR, повышение Order Completion Rate, улучшение Customer Satisfaction

## Предлагаемое решение

### **Технологии**:
- **Jaeger** - система трейсинга (Collector, Query, UI)
- **OpenTelemetry** - инструментация (Java SDK, .NET SDK)
- **Elasticsearch + Kibana** - хранилище и аналитика
- **RabbitMQ Tracing Plugin** - трейсинг сообщений

### **Инструментация**:
- **Java Spring Boot** (Shop API, CRM API) - Spring Cloud Sleuth
- **C# .NET** (MES API) - OpenTelemetry .NET SDK
- **RabbitMQ** - Tracing Plugin для сообщений

### **Компоненты**:
- **Новые**: Jaeger (Collector, Query, UI), Elasticsearch, Kibana
- **Доработка**: Shop API, CRM API, MES API, RabbitMQ

### **C4 диаграмма**: [alexandrit_tracing_c4.drawio](alexandrit_tracing_c4.drawio)
**Красные элементы**: Jaeger (Collector, Query, UI), Elasticsearch, Kibana
**Красные связи**: API → Jaeger Collector → Elasticsearch → Kibana

### **Мониторинг**:
- **Алерты**: Order Stuck, High Error Rate, Slow Processing, Message Loss
- **Действия**: Auto-retry, Escalation, Notifications, Ticket Creation

## Компромиссы

### **Ограничения**:
- **Производительность**: +1-2ms на запрос, +10-15% памяти
- **Стоимость**: Дополнительная инфраструктура
- **Сложность**: Обучение команды, поддержка системы
- **Legacy системы**: MES может потребовать доработки

### **Не поможет при**: Внешние API, проблемы сети, отказы оборудования

## Безопасность

### **Доступ**:
- **Аутентификация**: LDAP/AD интеграция, MFA
- **Авторизация**: Role-based (Support, Admin, Read-only)
- **Защита данных**: Шифрование, маскирование, логирование доступа
## Реализация

### **Этапы**:
1. **Инфраструктура** (2-3 недели) - Jaeger, Elasticsearch, Kibana
2. **Инструментация** (3-4 недели) - API трейсинг, RabbitMQ
3. **Мониторинг** (2-3 недели) - алерты, дашборды, интеграции
4. **Оптимизация** (2-3 недели) - sampling, производительность
