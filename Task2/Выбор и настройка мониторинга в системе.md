# Выбор и настройка мониторинга в системе

## Мотивация

### Проблемы без мониторинга
- **Отсутствие видимости**: Невозможно понять, где происходят сбои
- **Реактивный подход**: Проблемы обнаруживаются только после жалоб клиентов
- **Потеря контрактов**: Крупные клиенты уходят из-за нестабильности
- **Долгое время восстановления**: Без метрик сложно диагностировать проблемы

### Бизнес-ценность мониторинга
- **Проактивное решение проблем**: Обнаружение до влияния на пользователей
- **Сохранение клиентов**: Предотвращение потери контрактов из-за сбоев
- **Снижение операционных расходов**: Меньше времени на диагностику
- **Масштабируемость**: Данные для планирования роста нагрузки (+100 заказов/месяц)

## Выбор подхода к мониторингу

### RED подход (для API)
- **Rate**: RPS для каждого API (shop, CRM, MES)
- **Errors**: HTTP 4xx/5xx коды ответов
- **Duration**: Время ответа API

### USE подход (для инфраструктуры)
- **Utilization**: CPU%, Memory%, Disk I/O
- **Saturation**: Очереди, соединения к БД
- **Errors**: Сбои в работе компонентов

### Четыре золотых сигнала (для бизнес-метрик)
- **Latency**: Время расчета стоимости в MES
- **Traffic**: Количество заказов, активных пользователей
- **Errors**: Неудачные расчеты, потерянные заказы
- **Saturation**: Загрузка MES при расчетах

## План действий

### Этап 1: Инфраструктура мониторинга (2-3 недели)
- **Создать инстанс Prometheus** в облачной инфраструктуре
- **Настроить Grafana** для визуализации метрик
- **Установить Node Exporter** на все серверы
- **Настроить базовые алерты** для критичных метрик

### Этап 2: Интеграция с приложениями (3-4 недели)
- **Добавить Prometheus клиенты** в Java Spring Boot приложения
- **Настроить метрики** для C# MES приложения
- **Интегрировать RabbitMQ метрики** через RabbitMQ Exporter
- **Создать дашборды** для каждой команды

### Этап 3: Алертинг и автоматизация (2-3 недели)
- **Настроить AlertManager** для уведомлений
- **Создать правила алертов** для критичных ситуаций
- **Интегрировать с чатом/Email** для уведомлений
- **Настроить создание инцидентов** при превышении порогов
- **Настроить автоматические действия** (масштабирование, перезапуск)

### Этап 4: Оптимизация и расширение (4-6 недель)
- **Добавить бизнес-метрики** (количество заказов, время обработки)
- **Настроить retention политики** для хранения метрик
- **Создать отчеты** для бизнеса
- **Оптимизировать производительность** мониторинга

## Показатели насыщенности

### 🔴 Критичные пороги (немедленные действия)

#### MES API
- **CPU > 90%** → Автоматическое масштабирование + алерт в чат
- **Memory > 95%** → Перезапуск приложения + алерт в чат
- **Response time > 10 мин** → Алерт в чат + тикет в системе тикетов

#### Shop API
- **HTTP 500 > 10/мин** → Алерт в чат + автоматический перезапуск
- **Response time > 5 сек** → Алерт в чат + тикет в системе тикетов
- **CPU > 85%** → Алерт в чат + подготовка к масштабированию

#### RabbitMQ
- **Dead letter queue > 5 сообщений** → Алерт в чат + тикет в системе тикетов
- **Queue size > 1000 сообщений** → Алерт в чат + масштабирование консьюмеров

### 🟡 Предупреждающие пороги (планирование действий)

#### База данных
- **Connections > 80% от лимита** → Алерт в чат + планирование оптимизации
- **Disk usage > 85%** → Алерт в чат + планирование очистки
- **Memory > 90%** → Алерт в чат + планирование масштабирования

#### Хранилище
- **S3 usage > 90%** → Алерт в чат + планирование архивирования
- **Database size > 80%** → Алерт в чат + планирование партиционирования

### 🟢 Информационные пороги (мониторинг трендов)

#### Бизнес-метрики
- **RPS > 100/сек** → Логирование для анализа трендов
- **Active users > 200** → Логирование для планирования ресурсов
- **Storage growth > 10%/месяц** → Логирование для планирования инфраструктуры

## Автоматические действия

### При превышении критичных порогов:
1. **Автоматическое масштабирование** (если настроено)
2. **Алерт в чат** с деталями проблемы
3. **Создание инцидента** в системе управления инцидентами
4. **Создание тикета в системе тикетов** для команды разработки
5. **Уведомление DevOps** команды
6. **Автоматический перезапуск** проблемных сервисов

### При превышении предупреждающих порогов:
1. **Алерт в чат** с рекомендациями
2. **Создание задачи** для планирования оптимизации
3. **Создание инцидента** (низкий приоритет) для отслеживания
4. **Уведомление команды** о необходимости действий

### При превышении информационных порогов:
1. **Логирование** для анализа трендов
2. **Создание отчета** для бизнеса
3. **Планирование** долгосрочных улучшений
