# Планирование: анализ, идентификация проблем и поиск решений

## Проблемы архитектуры

| Категория | Проблема | Приоритет | Время |
|-----------|----------|-----------|-------|
| **Производительность** | Медленная загрузка MES дашборда, долгий расчет стоимости (2-3 мин) | 🔴 Высокий | 1-2 мес |
| **Масштабируемость** | +100 заказов/месяц, единичные инстансы, нет горизонтального масштабирования | 🔴 Высокий | 2-3 мес |
| **Интеграции** | Синхронные вызовы блокируют UI, проблемы с RabbitMQ | 🟡 Средний | 1-2 мес |
| **Надежность** | Нет резервирования, проблемы с заказами, отсутствие мониторинга | 🔴 Высокий | 1-2 мес |
| **Процессы** | Ручное тестирование, задержки релизов | 🟡 Средний | 2-4 мес |
| **Данные** | Нет кэширования, проблемы консистентности | 🟡 Средний | 1-3 мес |
| **Устойчивость** | Нет Circuit Breaker, Backpressure, Rate Limiting, Graceful Degradation | 🔴 Высокий | 1-2 мес |

## Решения

| Инициатива | Приоритет | Время | Описание |
|------------|-----------|-------|----------|
| **Мониторинг и алертинг** | 🔴 Критично | 1-2 мес | Prometheus + Grafana, метрики, алерты |
| **Circuit Breaker для MES** | 🔴 Критично | 1-2 мес | Защита от каскадных сбоев, fallback логика |
| **Rate Limiting + Graceful Degradation** | 🔴 Критично | 1-2 мес | Ограничение нагрузки, постепенная деградация |
| **Кэширование расчетов** | 🟡 Высокий | 1-2 мес | Redis кэш, TTL 24 часа |
| **Асинхронная обработка** | 🟡 Высокий | 2-3 мес | WebSocket уведомления, очереди задач |
| **Резервирование БД** | 🟡 Средний | 2-3 мес | Master-Slave репликация |
| **Автоматические тесты** | 🟡 Средний | 2-4 мес | Unit, Integration, E2E тесты |
| **Горизонтальное масштабирование** | 🟢 Низкий | 3-6 мес | Load Balancer, множественные инстансы |

## Топ-3 инициативы (ближайшие полгода)

### 1. Мониторинг и алертинг 🔴 Критично | 1-2 мес
**Почему**: Без видимости в систему невозможно понять, где именно происходят сбои.

**Что делать**:
- Prometheus + Grafana
- Метрики производительности
- Алерты на критические события
- Дашборды для каждой команды

### 2. Circuit Breaker для MES 🔴 Критично | 1-2 мес
**Почему**: Когда MES падает, это блокирует весь онлайн-магазин.

**Что делать**:
- Circuit Breaker между онлайн-магазином и MES
- Состояния: CLOSED → OPEN → HALF_OPEN
- Fallback: "Расчет временно недоступен"
- Настройка: 5 сбоев за 10 секунд → OPEN на 30 секунд

### 3. Rate Limiting + Graceful Degradation 🔴 Критично | 1-2 мес
**Почему**: После открытия B2B API система "завалило заказами".

**Что делать**:
- Rate Limiting: 100 req/min на клиента
- Graceful Degradation: отключение не-критичных функций при перегрузке
- Приоритизация: B2C > B2B > новые пользователи

## Целевая архитектура

| Период | Цели |
|--------|------|
| **1-2 мес** | Мониторинг, Circuit Breaker, Rate Limiting, кэширование |
| **3-4 мес** | Резервирование БД, автоматические тесты, CI/CD |
| **5-6 мес** | Горизонтальное масштабирование, готовность к 2x росту |

## Обоснование

**Почему эти 3 инициативы**:
- 🔴 **Мониторинг** - основа для всех решений, без видимости проблему не решить
- 🔴 **Circuit Breaker** - предотвращает каскадные сбои при падении MES
- 🔴 **Rate Limiting + Graceful Degradation** - защита от перегрузки после открытия B2B API

**Критерии выбора**:
- ✅ Не требуют кардинальных изменений архитектуры
- ✅ Реализуемы силами текущей команды
- ✅ Дают быстрый измеримый результат
- ✅ Прямо влияют на бизнес-метрики
