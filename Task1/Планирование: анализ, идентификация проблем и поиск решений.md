# Планирование: анализ, идентификация проблем и поиск решений

## Анализ текущей архитектуры

### Выявленные проблемы

#### 1. Проблемы производительности
- **Медленная загрузка MES дашборда**: операторы жалуются на долгую прогрузку первой страницы
- **Долгий расчет стоимости**: MES тратит 2-3 минуты на расчет, до 30 минут для сложных моделей
- **Проблемы с пагинацией и фильтрацией**: существующие решения не решили проблему производительности

#### 2. Проблемы масштабируемости
- **Линейный рост нагрузки**: +100 заказов в месяц, но архитектура не готова к росту
- **Единичные инстансы**: каждое приложение имеет только один инстанс
- **Отсутствие горизонтального масштабирования**: нет возможности увеличить количество инстансов

#### 3. Проблемы интеграции и коммуникации
- **Синхронная интеграция MES-онлайн-магазин**: расчет стоимости блокирует пользовательский интерфейс
- **Проблемы с RabbitMQ**: возможны потери сообщений или задержки в обработке
- **Отсутствие мониторинга интеграций**: нет видимости состояния очередей

#### 4. Проблемы надежности
- **Отсутствие резервирования**: единичные инстансы БД и приложений
- **Проблемы с заказами**: клиенты не получают заказы, статусы не обновляются
- **Отсутствие мониторинга**: нет системы отслеживания состояния системы

#### 5. Проблемы процессов разработки
- **Ручное тестирование**: QA не справляется с объемом, задержки релизов
- **Отсутствие автоматизации тестирования**: нет E2E автоматизации
- **Проблемы с деплоем**: ручные деплои в release/prod

#### 6. Проблемы с данными
- **Отсутствие кэширования**: повторные запросы к MES для расчета стоимости
- **Проблемы с консистентностью данных**: статусы заказов могут рассинхронизироваться
- **Отсутствие архивирования**: накопление данных в БД влияет на производительность

#### 7. Проблемы устойчивости к сбоям
- **Отсутствие Circuit Breaker**: каскадные сбои при падении MES
- **Нет Backpressure**: система не защищена от перегрузки
- **Отсутствие Bulkhead**: изоляция критических ресурсов
- **Нет Retry механизмов**: потерянные запросы при временных сбоях
- **Отсутствие Rate Limiting**: нет защиты от DDoS и злоупотреблений
- **Нет Graceful Degradation**: система падает полностью, а не деградирует постепенно

## Инициативы для решения проблем

### 1. Оптимизация производительности
- **Кэширование расчетов стоимости**: кэшировать результаты расчетов MES
- **Асинхронная обработка**: вынести расчет стоимости в фоновые задачи
- **Оптимизация запросов к БД**: индексы, оптимизация запросов в MES
- **CDN для статических ресурсов**: ускорить загрузку фронтенда

### 2. Масштабирование архитектуры
- **Горизонтальное масштабирование**: добавить возможность запуска нескольких инстансов
- **Load Balancer**: распределение нагрузки между инстансами
- **Микросервисная архитектура**: разделение монолитных приложений
- **Контейнеризация**: Docker для упрощения деплоя и масштабирования

### 3. Улучшение интеграций
- **Event-driven архитектура**: асинхронная обработка событий
- **API Gateway**: централизованное управление API
- **Улучшение RabbitMQ**: настройка кластера, мониторинг очередей
- **Retry механизмы**: обработка сбоев в интеграциях

### 4. Повышение надежности
- **Резервирование БД**: Master-Slave репликация
- **Мониторинг и алертинг**: Prometheus + Grafana
- **Health checks**: проверка состояния сервисов
- **Circuit Breaker**: защита от каскадных сбоев

### 4.1. Паттерны устойчивости (Resilience Patterns)
- **Circuit Breaker для MES**: защита от каскадных сбоев при падении MES
- **Backpressure для RabbitMQ**: контроль потока сообщений, предотвращение перегрузки
- **Bulkhead изоляция**: отдельные пулы ресурсов для критических операций
- **Retry с экспоненциальной задержкой**: обработка временных сбоев
- **Timeout и Fallback**: таймауты для внешних вызовов, fallback логика
- **Rate Limiting/Throttling**: ограничение скорости запросов к API
- **Graceful Degradation**: постепенное снижение функциональности при перегрузке

### 5. Автоматизация процессов
- **CI/CD пайплайн**: автоматизация тестирования и деплоя
- **Автоматические тесты**: Unit, Integration, E2E тесты
- **Blue-Green деплой**: безопасные обновления
- **Infrastructure as Code**: Terraform для управления инфраструктурой

### 6. Улучшение данных
- **Архивирование старых данных**: перенос в холодное хранилище
- **Партиционирование таблиц**: разделение данных по времени
- **Read replicas**: отдельные инстансы для чтения
- **Data Lake**: централизованное хранилище данных

## Топ-3 инициативы на ближайшие полгода

### 1. Мониторинг и алертинг (критично)
**Почему**: Без видимости в систему невозможно понять, где именно происходят сбои. Это основа для всех остальных улучшений.

**Что делать**:
- Настроить Prometheus + Grafana
- Добавить метрики производительности
- Настроить алерты на критические события
- Создать дашборды для каждой команды

### 2. Circuit Breaker для MES (защита от каскадных сбоев)
**Почему**: Когда MES падает, это блокирует весь онлайн-магазин. Circuit Breaker предотвращает каскадные сбои.

**Что делать**:
- Реализовать Circuit Breaker между онлайн-магазином и MES
- Состояния: CLOSED → OPEN → HALF_OPEN
- Fallback: показывать "Расчет временно недоступен, попробуйте позже"
- Метрики: количество сбоев, время восстановления
- Настройка: 5 сбоев за 10 секунд → OPEN на 30 секунд

### 3. Rate Limiting + Graceful Degradation (защита от перегрузки)
**Почему**: После открытия B2B API система "завалило заказами". Нужна защита от перегрузки и постепенная деградация функциональности.

**Что делать**:
- **Rate Limiting**: ограничение запросов к API (100 req/min на клиента)
- **Graceful Degradation**: при перегрузке отключать не-критичные функции
  - Отключить конструктор 3D-моделей (оставить только загрузку файлов)
  - Упростить расчет стоимости (базовые материалы)
  - Ограничить количество одновременных расчетов
- **Приоритизация**: B2C клиенты > B2B клиенты > новые пользователи
- **Мониторинг**: отслеживание нагрузки и автоматическое включение ограничений

### 1. Мониторинг и алертинг
### 2. Кэширование расчетов стоимости (высокий бизнес-импакт)
**Почему**: Прямо влияет на пользовательский опыт. Клиенты не будут ждать 2-3 минуты каждый раз.

**Что делать**:
- Redis для кэширования результатов расчетов
- Ключ кэша: хеш от параметров модели + материалов
- TTL кэша: 24 часа (цены материалов могут меняться)
- Fallback на MES при отсутствии в кэше

### 3. Асинхронная обработка расчетов (улучшение UX)
**Почему**: Убирает блокировки UI, позволяет пользователю продолжать работу, пока идет расчет.

**Что делать**:
- WebSocket для уведомлений о готовности расчета
- Очередь задач для расчетов
- Статус "Расчет в процессе" в UI
- Уведомление пользователя о готовности результата

## Обоснование выбора

### Основной топ-3 (с Circuit Breaker и Backpressure):

1. **Мониторинг** - дает видимость и позволяет принимать обоснованные решения
2. **Circuit Breaker** - критически важен для предотвращения каскадных сбоев
3. **Backpressure** - защищает систему от перегрузки при росте нагрузки

### Почему именно эти паттерны:

**Circuit Breaker**:
- Решает проблему "завалило заказами" - защищает MES от перегрузки
- Предотвращает каскадные сбои при падении MES
- Дает системе время на восстановление
- Улучшает пользовательский опыт (fallback вместо зависания)

**Rate Limiting + Graceful Degradation**:
- Критически важен после открытия B2B API ("завалило заказами")
- Rate Limiting защищает от перегрузки API
- Graceful Degradation позволяет системе работать частично, а не падать полностью
- Приоритизация клиентов: B2C > B2B > новые пользователи
- Автоматическое управление нагрузкой в зависимости от состояния системы

### Альтернативный топ-3 (если Circuit Breaker уже есть):

1. **Мониторинг** - основа для всех решений
2. **Кэширование** - решает самую болезненную проблему для пользователей (2-3 минуты ожидания)
3. **Асинхронность** - кардинально улучшает пользовательский опыт

### Все инициативы:
- Не требуют кардинальных изменений архитектуры
- Могут быть реализованы силами текущей команды
- Дают быстрый и измеримый результат
- Создают основу для дальнейших улучшений
- Прямо влияют на бизнес-метрики (удовлетворенность клиентов, время обработки заказов)
