# Архитектурное решение по кешированию

## Анализ системы для кеширования

### **Проблемные области**:
- **MES API** - медленная загрузка списка заказов
- **Shop API** - медленный расчет стоимости (2-3 минуты)
- **CRM API** - медленное обновление статусов заказов
- **Databases** - частые запросы к одним и тем же данным

### **Кандидаты для кеширования**:
- **Список заказов** - часто запрашивается операторами
- **Статусы заказов** - часто обновляются и читаются
- **Расчеты стоимости** - долгие вычисления (2-3 минуты)
- **Справочные данные** - редко изменяются

## Мотивация

### **Проблемы**:
- **Низкая производительность MES** - операторы жалуются на медленную работу
- **Медленные расчеты стоимости** - клиенты недовольны временем ожидания
- **Высокая нагрузка на БД** - частые запросы к одним данным
- **Плохой UX** - долгая загрузка страниц

### **Решение**:
- **Серверное кеширование** - Redis для быстрого доступа к данным
- **Клиентское кеширование** - браузерный кеш для статических ресурсов
- **Кеширование расчетов** - сохранение результатов вычислений

### **Влияние на метрики**:
- **Response Time** - значительное снижение
- **Database Load** - существенное снижение
- **User Satisfaction** - повышение
- **System Throughput** - повышение

## Предлагаемое решение

### **Тип кеширования**:
- **Серверное кеширование** - Redis для серверных данных
- **Клиентское кеширование** - браузерный кеш для статики

### **Паттерны кеширования**:

#### **Cache-Aside (Lazy Loading)**:
- **Применение**: Список заказов, статусы заказов
- **Логика**: Приложение проверяет кеш → если нет, загружает из БД → сохраняет в кеш
- **Плюсы**: Простота, контроль над данными
- **Минусы**: Cache miss при первом запросе

#### **Write-Through**:
- **Применение**: Обновление статусов заказов
- **Логика**: Запись в БД → обновление кеша
- **Плюсы**: Консистентность данных
- **Минусы**: Медленнее записи

#### **Refresh-Ahead**:
- **Применение**: Расчеты стоимости (предварительная загрузка)
- **Логика**: Обновление кеша до истечения TTL
- **Плюсы**: Всегда актуальные данные
- **Минусы**: Сложность реализации

### **Стратегия инвалидации**:

#### **Временная инвалидация (TTL)**:
- **Применение**: Список заказов (5 минут), статусы (1 минута)
- **Логика**: Автоматическое удаление по времени
- **Плюсы**: Простота, автоматическая очистка
- **Минусы**: Может быть неактуальным

#### **Инвалидация по ключу**:
- **Применение**: Обновление статуса заказа
- **Логика**: Удаление конкретного ключа при изменении
- **Плюсы**: Точная инвалидация
- **Минусы**: Сложность отслеживания зависимостей

#### **Программная инвалидация**:
- **Применение**: Критичные изменения данных
- **Логика**: Принудительная очистка кеша
- **Плюсы**: Полный контроль
- **Минусы**: Ручное управление

### **Сравнительный анализ стратегий**:

| Стратегия | TTL | По ключу | Программная |
|-----------|-----|----------|-------------|
| **Простота** | Высокая | Средняя | Низкая |
| **Консистентность** | Средняя | Высокая | Высокая |
| **Производительность** | Высокая | Высокая | Средняя |
| **Контроль** | Низкий | Высокий | Полный |

### **Выбранная стратегия**: Комбинированная
- **TTL** для большинства данных (простота)
- **По ключу** для критичных изменений (консистентность)
- **Программная** для экстренных случаев (контроль)

## Диаграмма последовательности

### **Чтение списка заказов**:
```
Operator → MES API → Redis Cache
                ↓ (cache miss)
                MES DB → Redis Cache → Operator
```

### **Обновление статуса заказа**:
```
CRM API → MES DB → Invalidate Cache → Redis Cache
                ↓
            Notify MES API → Update Cache
```

## Технические детали

### **Redis конфигурация**:
- **Memory**: 4GB для кеша
- **Persistence**: RDB + AOF для надежности
- **Clustering**: Master-Slave для отказоустойчивости
- **TTL**: Настраиваемый для разных типов данных

### **Кешируемые данные**:
- **Список заказов**: 5 минут TTL
- **Статусы заказов**: 1 минута TTL
- **Расчеты стоимости**: 30 минут TTL
- **Справочники**: 1 час TTL
- **Сессии**: 24 часа TTL

### **Мониторинг**:
- **Hit Rate** - процент попаданий в кеш
- **Miss Rate** - процент промахов
- **Memory Usage** - использование памяти
- **Response Time** - время отклика кеша

## Реализация

### **Этапы внедрения**:
1. **Настройка Redis** - инфраструктура и конфигурация
2. **Кеширование списка заказов** - MES API
3. **Кеширование статусов** - CRM API
4. **Кеширование расчетов** - Shop API
5. **Мониторинг и оптимизация** - настройка TTL и алертов

### **Ожидаемые результаты**:
- **Снижение времени загрузки** списка заказов с 10 секунд до 1 секунды
- **Ускорение расчетов** стоимости за счет кеширования результатов
- **Снижение нагрузки** на базу данных на 70%
- **Повышение производительности** системы в целом
