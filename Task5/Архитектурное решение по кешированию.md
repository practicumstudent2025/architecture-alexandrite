# Архитектурное решение по кешированию

## Анализ системы для кеширования

### **Проблемные области**:
- **MES API** - медленная загрузка списка заказов
- **Shop API** - медленный расчет стоимости (2-3 минуты)
- **CRM API** - медленное обновление статусов заказов
- **Databases** - частые запросы к одним и тем же данным
- **RabbitMQ** - медленная обработка сообщений между системами
- **S3 Storage** - медленная загрузка/скачивание 3D-моделей
- **Frontend Applications** - медленная загрузка статических ресурсов

### **Кандидаты для кеширования**:
- **Список заказов** - часто запрашивается операторами
- **Статусы заказов** - часто обновляются и читаются
- **Расчеты стоимости** - долгие вычисления (2-3 минуты)
- **Справочные данные** - редко изменяются
- **3D-модели** - медленная загрузка из S3
- **Статические ресурсы** - CSS, JS, изображения
- **Пользовательские сессии** - аутентификация
- **Сообщения RabbitMQ** - кеширование для быстрой обработки

## Мотивация

### **Проблемы**:
- **Низкая производительность MES** - операторы жалуются на медленную работу
- **Медленные расчеты стоимости** - клиенты недовольны временем ожидания
- **Высокая нагрузка на БД** - частые запросы к одним данным
- **Плохой UX** - долгая загрузка страниц

### **Решение**:
- **Серверное кеширование** - Redis для быстрого доступа к данным
- **Клиентское кеширование** - браузерный кеш для статических ресурсов
- **Кеширование расчетов** - сохранение результатов вычислений

### **Влияние на метрики**:
- **Response Time** - значительное снижение
- **Database Load** - существенное снижение
- **User Satisfaction** - повышение
- **System Throughput** - повышение

## Предлагаемое решение

### **Выбор типа кеширования**:

#### **Серверное кеширование (Redis)**:
- **Применение**: Список заказов, статусы, расчеты стоимости, справочники
- **Почему именно серверное**: 
  - Данные часто запрашиваются разными пользователями
  - Нужна консистентность между пользователями
  - Серверный кеш доступен всем клиентам
  - Централизованное управление инвалидацией

#### **Клиентское кеширование (Browser)**:
- **Применение**: Статические ресурсы (CSS, JS, изображения), 3D-модели
- **Почему именно клиентское**:
  - Статические ресурсы не изменяются часто
  - Снижает нагрузку на сервер
  - Ускоряет загрузку страниц
  - Экономит трафик

### **Выбор паттернов кеширования**:

#### **Cache-Aside (выбран для большинства случаев)**:
- **Применение**: Список заказов, статусы заказов, справочники
- **Почему выбран**:
  - Простота реализации и понимания
  - Полный контроль над логикой кеширования
  - Легко отлаживать и мониторить
  - Гибкость в настройке TTL
- **Почему не подходят другие**:
  - **Write-Through**: Слишком медленный для частых обновлений
  - **Refresh-Ahead**: Сложность реализации, избыточность для большинства данных

#### **Write-Through (выбран для критичных данных)**:
- **Применение**: Обновление статусов заказов
- **Почему выбран**:
  - Гарантирует консистентность данных
  - Критично для бизнес-логики
  - Пользователи должны видеть актуальные статусы
- **Почему не подходят другие**:
  - **Cache-Aside**: Риск неконсистентности при обновлениях
  - **Refresh-Ahead**: Избыточная сложность для простых обновлений

#### **Refresh-Ahead (выбран для расчетов)**:
- **Применение**: Расчеты стоимости (2-3 минуты обработки)
- **Почему выбран**:
  - Расчеты дорогие по времени
  - Пользователи ожидают быстрый результат
  - Предварительная загрузка улучшает UX
- **Почему не подходят другие**:
  - **Cache-Aside**: Пользователь ждет 2-3 минуты при cache miss
  - **Write-Through**: Не применимо для read-only расчетов

### **Обоснование выбора паттернов**:

| Паттерн | Применение | Почему выбран | Почему другие не подходят |
|---------|------------|---------------|---------------------------|
| **Cache-Aside** | Список заказов, справочники | Простота, контроль | Write-Through медленный, Refresh-Ahead избыточен |
| **Write-Through** | Статусы заказов | Консистентность | Cache-Aside рискован, Refresh-Ahead сложен |
| **Refresh-Ahead** | Расчеты стоимости | Быстрый результат | Cache-Aside медленный, Write-Through не применим |

### **Стратегия инвалидации кеша**:

#### **Временная инвалидация (TTL)**:
- **Применение**: Список заказов (5 минут), справочники (1 час)
- **Почему подходит**:
  - Простота реализации и управления
  - Автоматическая очистка устаревших данных
  - Подходит для данных, которые не критичны к актуальности
- **Почему другие не подходят**:
  - **По ключу**: Избыточная сложность для справочников
  - **Программная**: Ручное управление неэффективно

#### **Инвалидация по ключу**:
- **Применение**: Статусы заказов, расчеты стоимости
- **Почему подходит**:
  - Точная инвалидация только измененных данных
  - Гарантирует актуальность критичных данных
  - Эффективно для часто обновляемых данных
- **Почему другие не подходят**:
  - **TTL**: Может быть неактуальным для статусов
  - **Программная**: Слишком грубое управление

#### **Программная инвалидация**:
- **Применение**: Экстренные случаи, массовые изменения
- **Почему подходит**:
  - Полный контроль над кешем
  - Быстрая очистка при критичных изменениях
  - Резервный механизм для других стратегий
- **Почему другие не подходят**:
  - **TTL**: Слишком медленно для экстренных случаев
  - **По ключу**: Сложно отследить все зависимости

### **Сравнительный анализ стратегий инвалидации**:

| Стратегия | TTL | По ключу | Программная |
|-----------|-----|----------|-------------|
| **Простота** | Высокая | Средняя | Низкая |
| **Консистентность** | Средняя | Высокая | Высокая |
| **Производительность** | Высокая | Высокая | Средняя |
| **Контроль** | Низкий | Высокий | Полный |
| **Применение** | Справочники | Статусы | Экстренные случаи |

### **Выбранная стратегия**: Комбинированная
- **TTL** для справочников и списков (простота)
- **По ключу** для статусов и расчетов (консистентность)
- **Программная** для экстренных случаев (контроль)

## Диаграмма последовательности

### **Чтение списка заказов (Cache-Aside)**:
```
Operator → MES API → Redis Cache (проверка кеша)
                ↓ (cache hit)
                Redis Cache → MES API → Operator (быстрый ответ)
                
                ↓ (cache miss)
                MES API → MES DB (запрос к БД)
                MES DB → MES API (данные)
                MES API → Redis Cache (сохранение в кеш)
                MES API → Operator (ответ)
```

**Участники кеширования**: Operator, MES API, Redis Cache, MES DB

### **Обновление статуса заказа (Write-Through)**:
```
CRM API → MES DB (запись в БД)
MES DB → CRM API (подтверждение)
CRM API → Redis Cache (обновление кеша)
Redis Cache → CRM API (подтверждение)
CRM API → Operator (уведомление об обновлении)
```

**Участники кеширования**: CRM API, MES DB, Redis Cache, Operator

### **Расчет стоимости (Refresh-Ahead)**:
```
Background Job → MES API (предварительный расчет)
MES API → MES DB (сложные вычисления)
MES DB → MES API (результат)
MES API → Redis Cache (сохранение результата)
                ↓
Customer → Shop API → Redis Cache (быстрый ответ)
Redis Cache → Shop API → Customer (мгновенный результат)
```

**Участники кеширования**: Background Job, MES API, MES DB, Redis Cache, Shop API, Customer

### **Загрузка статических ресурсов (Client-Side)**:
```
Customer → Browser (запрос CSS/JS)
Browser → Browser Cache (проверка кеша)
                ↓ (cache hit)
                Browser Cache → Customer (быстрая загрузка)
                
                ↓ (cache miss)
                Browser → Shop API (запрос ресурса)
                Shop API → Browser (ресурс)
                Browser → Browser Cache (сохранение)
                Browser → Customer (отображение)
```

**Участники кеширования**: Customer, Browser, Browser Cache, Shop API

## Технические детали

### **Redis конфигурация**:
- **Memory**: 4GB для кеша
- **Persistence**: RDB + AOF для надежности
- **Clustering**: Master-Slave для отказоустойчивости
- **TTL**: Настраиваемый для разных типов данных

### **Кешируемые данные**:
- **Список заказов**: 5 минут TTL
- **Статусы заказов**: 1 минута TTL
- **Расчеты стоимости**: 30 минут TTL
- **Справочники**: 1 час TTL
- **Сессии**: 24 часа TTL

### **Мониторинг**:
- **Hit Rate** - процент попаданий в кеш
- **Miss Rate** - процент промахов
- **Memory Usage** - использование памяти
- **Response Time** - время отклика кеша

## Дополнительное задание: Альтернативные решения

### **Решение 1: Гибридное кеширование (Redis + Memcached)**
- **Описание**: Использование Redis для сложных данных + Memcached для простых кешей
- **Диаграмма**: 
```
API → Redis (сложные данные) → Database
API → Memcached (простые кеши) → Database
```

#### **Плюсы**:
- Специализация инструментов под задачи
- Memcached быстрее для простых операций
- Redis лучше для сложных структур данных
- Оптимальное использование ресурсов

#### **Минусы**:
- Сложность управления двумя системами
- Увеличение операционных расходов
- Сложность синхронизации между кешами
- Дополнительная инфраструктура

### **Решение 2: Распределенное кеширование (Redis Cluster)**
- **Описание**: Кластер Redis для горизонтального масштабирования кеша
- **Диаграмма**:
```
API → Redis Cluster (3+ узла) → Database
```

#### **Плюсы**:
- Высокая доступность и отказоустойчивость
- Горизонтальное масштабирование
- Распределение нагрузки
- Подходит для больших объемов данных

#### **Минусы**:
- Сложность настройки и управления
- Высокие требования к ресурсам
- Сложность обеспечения консистентности
- Избыточность для текущих потребностей

### **Сравнительный анализ решений**:

| Критерий | Гибридное (Redis + Memcached) | Распределенное (Redis Cluster) | Текущее (Redis) |
|----------|-------------------------------|--------------------------------|-----------------|
| **Простота** | Низкая | Низкая | Высокая |
| **Производительность** | Высокая | Высокая | Высокая |
| **Масштабируемость** | Средняя | Высокая | Средняя |
| **Стоимость** | Высокая | Высокая | Низкая |
| **Сложность** | Высокая | Высокая | Низкая |
| **Отказоустойчивость** | Средняя | Высокая | Средняя |

### **Заключение**:

**Выбранное решение: Текущее (Redis)** является оптимальным по следующим причинам:

1. **Соответствие потребностям**: Текущие объемы данных не требуют сложных решений
2. **Простота внедрения**: Быстрое развертывание и настройка
3. **Экономическая эффективность**: Минимальные операционные расходы
4. **Достаточная производительность**: Redis покрывает все текущие потребности
5. **Простота поддержки**: Команда может легко управлять одним инструментом

**Альтернативные решения** можно рассмотреть в будущем при:
- Росте объемов данных в 10+ раз
- Требованиях к высокой доступности (99.99%+)
- Необходимости сложной аналитики кеша
- Планах масштабирования на несколько регионов
